# 共用埋點規則

跨 app 一致的部分。**模組代碼表不在這裡** —— 那是各 app 的功能地圖，各自維護（見 `module-table.md`）。改動這份需要事業群層級同意；參數白名單則是公司後端 behavior-log API 的事實，本來就全公司一致。

## 1. 事件命名：三段式

```
module_object_action
```

| 段 | 規則 | 例 |
|---|---|---|
| module | 全小寫**完整單字**，只能從該 app 的模組代碼表挑，不可自創 | `home`、`invoice` |
| object | camelCase 名詞，畫面上被操作的東西；整頁用 `page` | `allTimeChip`、`creditCard` |
| action | **過去式動詞**，只能從下面的動詞表挑 | `clicked`、`switched` |

- 最多四段，能用參數就不要加第四段。
- 只用小寫英數與底線；不用大寫縮寫（`HPG`、`WGT` 這類不再新增）。
- 事件名總長 40 字元內。

## 2. 動詞表

`clicked`（點擊）、`switched`（並列選項間切換）、`changed`（值改成另一個值）、`closed`（關閉彈窗／橫幅）、`swiped`（滑動）、`entered`（進入頁面）、`showed`（系統讓東西出現）、`viewed`（使用者真的看到＝曝光）、`accepted`／`rejected`（二選一彈窗的肯定／否定）、`confirmed`（有後果的確認）、`submitted`（送出表單）、`claimed`（領取）、`succeeded`／`failed`（流程成功／失敗結束）。

重複語意收斂：彈窗二選一用 accepted／rejected，有後果的確認用 confirmed；`refused` 不再新增。

## 3. 參數

- 參數名一律 camelCase，**不可有空格**（`content type` 是既有錯誤，正確為 `contentType`）。
- 優先用標準 key：`type`（類別／分組）、`from`（來源或切換前）、`to`（切換後）、`source`、`contentType`、`count`、`value`、`url`。
- **自創沒登記的 key 後端會丟棄**，資料直接沒了。新 key 走登記：PM 提出 → 數據分析確認 → 白名單更新。
- **絕不放個資**：姓名、手機、Email、發票號碼、金額明細。使用者識別由框架自動帶入。

## 4. 用參數，不要用事件名

兩個事件只有一個維度不同、其餘完全一樣 → 那個維度是參數。錯誤示範：`report_time_month` / `report_time_half_year` / `report_time_year` 三個事件；正確：`report_timeRange_switched` + `to: month / halfYear / year`。一次性活動是否共用一個 `campaign` 模組帶 `type` 參數，**由各 app 的 PM 依活動頻率裁決**（簡單記帳 2026-08-27 裁決：不常辦活動，先不設統一模組）。

## 5. 發送規則（寫進 HANDOFF 時逐條對照）

1. **只有跨狀態的切換才送。** 同狀態內的變化不送 —— 月份之間換月不是切換期間。把事件綁到所有點擊上，會把「切換」灌成「每次操作」。
2. **一次操作只送一次。** 提交後的 outcome 節點、收合計時器等後續狀態不是新的使用者操作，在那些節點上重複送會灌水。
3. **系統自動行為預設不送。** App 重開的狀態還原、背景同步不是使用者切換的。要送必須是 PM 明確裁決、並以參數標明來源（例：`from: auto`）。
4. **重複觸發且無狀態變化，預設不送。** 已在某狀態再點一次進入該狀態的按鈕（沒有發生任何切換）→ 建議不送，列待 PM 確認。

## 6. 沿用政策（scope）

| 情況 | 怎麼辦 |
|---|---|
| 這個行為**已經有事件** | **沿用原名** —— 即使名字不合規範、即使這次是大改版。行為搬家（換元件、換位置）語意不變也算沿用 |
| 既有事件**加新參數值** | 跟著既有事件走，照它原本的格式 |
| 需要**全新事件名** | 套本規範，標 `v1` |

改名等同全新事件，歷史數據斷掉、現行報表失效 —— 而改版正是最需要對比歷史的時候。新舊怎麼區分由各 app 的 PM 決定：加一欄「命名規範版本」（`legacy`／`v1`），或以規範生效日為分界（簡單記帳 2026-08-27 裁決：不加欄，以日期分界）。真要改名：先通知數據分析窗口確認沒有報表在追，並記舊名→新名對照。

## 7. 假設反推（決定要埋什麼）

埋點的起點是假設，不是設計稿上的元件。對每個假設問四題：

1. **數據長相**：假設成立／不成立各長什麼樣？說不出具體可量測的差異＝假設還沒準備好被驗證。
2. **最小 event 集**：看出差異最少需要幾個 event？刻意求少。
3. **切分參數**：事後想分組看的維度，當下就要當參數埋，**事後補不回來**。
4. **對照組**：A/B 實驗的留存／轉換 event 對照組也要埋，否則沒有基準。

兩類掃元件永遠掃不到、卻最關鍵的 event：分組標記／session 類、後端事件（伺服器狀態變化、交易結果）。
