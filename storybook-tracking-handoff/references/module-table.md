# 模式 A：從既有埋點表歸納模組代碼表

每個 app 跑一次。輸入是該 app 的既有埋點清單，輸出兩樣：**模組代碼表草案**（給 PM 與數據分析確認）與**既有清單問題清單**（只回報，不修）。

## 1. 拿到清單

Google Sheet 公開連結可直接抓指定工作表的 CSV，不用 API key：

```sh
curl -sSLG "https://docs.google.com/spreadsheets/d/<SHEET_ID>/gviz/tq" \
  --data-urlencode "tqx=out:csv" \
  --data-urlencode "sheet=<工作表名稱>" -o track.csv
```

`/export?format=csv` 只會給第一個工作表 —— 要指定工作表必須走 `gviz/tq`。

## 2. 解析

常見的表結構：事件名那一列帶完整欄位，**下方的空白列是該事件的參數值** —— 解析時前置欄位要 forward-fill（往下沿用上一個非空值），參數列歸屬到上一個事件。先印出前 20 列人工確認結構再寫解析，每張表的欄位都不一樣。

## 3. 歸納模組

1. 依「對應頁面／區塊」分組，統計每組事件的**名稱第一段**（事實上的 module）。
2. 為每組提一個**全小寫完整單字**代碼；舊的大寫縮寫放進「過去出現過的寫法」對照欄，不刪。
3. 兩個必要判斷（都要 PM 拍板，寫成明確問題不要自己決定）：
   - **權限不是模組。**「進階功能／VIP」這類分區底下的事件通常各有功能歸屬，拆回去；是不是付費才能用，改用參數記。
   - **每檔活動不各開一個模組。** 一次性活動統一收在 `campaign`，帶 `type` 參數區分哪一檔；長期功能才各自登記。

## 4. 問題清單（必掃五類）

| 類 | 找法 |
|---|---|
| 前綴撞名 | 同一個名稱第一段被多個頁面分組使用 |
| 重複事件名 | 完全相同的事件名出現多次 |
| 拼字錯誤 | 逐個唸過；已上線通常不改，但要標記 |
| 維度寫進名字 | 一組事件只差一個維度（`*_month`／`*_year`）→ 應為一事件加參數 |
| 參數 key 帶空格或大小寫混亂 | 對照 tracking-rules.md §3 |

**只回報，不修。** 既有事件依沿用政策一律不動；這份清單的用途是讓新事件別再重蹈，以及讓 PM 知道表的實際狀態。

## 5. 統計「已符合規範」的比例

算出既有事件裡本來就符合三段式的有幾個，寫進交給 PM 的報告 —— 這個數字決定「命名規範版本」欄（`legacy`／`v1`）有多必要。經驗值：長年累積的表通常低於 5%。

## 6. 交付

一頁報告：模組代碼表草案（含舊寫法對照欄）＋ 兩個待拍板判斷 ＋ 問題清單 ＋ 合規比例。PM 與數據分析確認後，這份就是該 app 的命名規範附表，與 `tracking-rules.md` 合起來構成完整規範。
